# Data Model and Cryptographic Formats

## Persistent account data (PostgreSQL)

### Account

| Field | Type | Rules |
|---|---|---|
| `id` | UUID | Primary key; generated by the backend |
| `email_normalized` | VARCHAR(320) | Required, unique, normalized once consistently |
| `password_hash` | VARCHAR(255) | Required adaptive one-way hash; never plaintext |
| `verified_at` | TIMESTAMP WITH TIME ZONE | Null until email verification succeeds |
| `verification_token_hash` | BYTEA | Nullable; digest only, single-use |
| `verification_expires_at` | TIMESTAMP WITH TIME ZONE | Nullable; at most 24 hours after issuance |
| `public_key_pem` | TEXT | Nullable SPKI PEM; public material only |
| `created_at` | TIMESTAMP WITH TIME ZONE | Required |

An account may sign in and use messaging only after `verified_at` is set. Verification consumes the token atomically, clears both token fields, and establishes the authenticated session. The raw token is high-entropy random data sent only in the verification link. A new verification request replaces the previous digest/expiry. Normalize an address by trimming and lowercasing it with `Locale.ROOT`; do not rewrite provider-specific dots or plus tags. Password and email input bounds are enforced before storage.

Verification email resends are limited to one per normalized address per minute and five per hour. A throttled request returns the same generic response as unknown or already-verified addresses.

### Data deliberately not modeled

There is no message, conversation, file, private-key, private-key-password, ciphertext, or offline-delivery entity/table. A message envelope exists only in browser memory and the transient WebSocket relay path. The public key is saved to allow recipient lookup; the private key remains local.

## In-memory browser domain objects

### Recipient key pair

- `publicKey`: Web Crypto `CryptoKey`, RSA-OAEP/SHA-256, SPKI PEM; may be registered with the account.
- `privateKey`: Web Crypto `CryptoKey`, RSA-OAEP/SHA-256; imported from `.rsakey`, never transmitted or persisted by the server.

### Encrypted direct message (version 1)

UTF-8 JSON envelope transported as opaque STOMP application data:

```json
{
  "version": 1,
  "keyEncryption": {
    "name": "RSA-OAEP",
    "hash": "SHA-256",
    "wrappedKey": "<base64 AES-256 key>"
  },
  "contentEncryption": {
    "name": "AES-GCM",
    "length": 256,
    "iv": "<base64 12-byte IV>",
    "tagLength": 128
  },
  "ciphertext": "<base64 UTF-8 message bytes and GCM tag>"
}
```

Generate a fresh AES key and IV for every message. The sender encrypts locally using `TextEncoder`; the recipient decodes only after successful GCM authentication. The server separately validates the recipient account and routes the unchanged bounded envelope. Neither the sender ID nor plaintext is accepted as trusted message content. Encryption does not authenticate the sender.

### Encrypted file container (`.rsaenc`, v1)

All integers are unsigned big-endian. Container layout:

| Offset | Size | Meaning |
|---|---:|---|
| 0 | 8 | ASCII magic `RSAENC01` |
| 8 | 4 | Metadata JSON byte length; must be 1–8192 |
| 12 | header length | UTF-8 JSON metadata |
| after header | remaining bytes | AES-256-GCM ciphertext followed by 16-byte tag |

The exact bytes from offset 0 through the last metadata byte are AES-GCM `additionalData`. Header fields are `version`, `keyEncryption`, `contentEncryption`, and optional original filename/MIME type. Each operation uses a fresh AES key and IV. Maximum source size is 50 MiB.

### Protected private-key envelope (`.rsakey`, v1)

UTF-8 JSON envelope with format/version, PBKDF2-HMAC-SHA-256 parameters, 16-byte random salt, AES-256-GCM 12-byte IV, and encrypted PKCS#8 DER. The key derivation uses 600,000 iterations; passphrase length is at least 12 characters. Authenticate the canonical envelope metadata as AAD; validate bounds before deriving a key. This is an application-specific encrypted export, not standardized encrypted PKCS#8.

## Health response

`GET /api/health` returns `200 {"status":"UP"}` without database credentials, keys, files, or message data.

## Validation and retention rules

- Reject unknown versions, algorithms, malformed base64, missing fields, oversized inputs, invalid keys, and malformed JSON before expensive operations.
- A malformed, altered, wrong-key, or wrong-password payload fails without partial plaintext or download.
- Normalize account email consistently for account uniqueness, authentication principal, and recipient lookup.
- Hash verification tokens before writing them; clear token digests and expiration when consumed or replaced.
- Do not log account passwords, verification tokens/links, file bytes, plaintext, private keys, ciphertext, or full message envelopes.
- Do not keep an in-memory queue or replay messages for offline users. A disconnected recipient has no later delivery.
